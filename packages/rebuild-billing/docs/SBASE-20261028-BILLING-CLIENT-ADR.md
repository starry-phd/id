## ADR D-03 — RevenueCat vs self-managed Apple/Google server validation

| Criterion | Option A: RevenueCat SDK + webhook (candidate recommendation) | Option B: self-built native IAP + Workers Store Server |
|---|---|---|
| Single purchase authority | RevenueCat may aggregate Store evidence; DEV-B canonical backend still validates accepted events and owns scoped entitlement state | DEV-B backend validates Apple/Google official source itself; one canonical writer |
| Identity and app scoping | Backend checks Starry Auth mapped identity, app_id, bundle/package, product ID, Store app, environment before entitlement; never trust mobile customerId alone | Same checks, additional Store signed transaction/token ingestion and anti-replay owned by DEV-B |
| Lifecycle | Map renew, refund, revoke, hold, grace, expire, restore, replay, missing webhook and eventual reconciliation; preserve original store transaction references behind protected backend | Implement and maintain all Store lifecycle/ACK, retries, reconciliation and incident recovery separately |
| Offline/cache | Cached RevenueCat client status is UI hint ONLY; no paid access/ads off without current backend authoritative verification | Cached client receipt is UI hint ONLY; backend evidence required |
| Operations/cost | Vendor pricing, webhook delivery and native SDK compatibility D-01/D-06/region must be verified at decision time | Higher maintenance/oncall and legal/Store policy burden; official Apple/Google server access, sandbox and test devices needed |
| Provider exit / rollback | Export lawful purchase lineage and source versions; dual-run read-only shadow before cut-over, one active backend writer at a time; rollback to prior verified verifier without regrant | Keep canonical Store history and protected identity mapping; cut-over only after matching version and refunds/chargebacks |

**Decision:** No provider selected. **Neither adapter is installed**. No RevenueCat credentials, Webhooks, StoreKit/Play Billing SDK, EAS, SKU, billing product or actual paid features configured. RevenueCat is candidate per source; independent offline tests cannot prove vendor policy, Store signature or refund settlement. Select only after owner ADR, dev-build PoC, lawful identity/retention + reconciled signed Store evidence + approval.

## Actual new v0 contract and safety model

- `src/sbase-billing-client-candidate.ts` exports `createSbaseOfflineBillingClient`: typed `purchase(productKey)`, `getOfferings`, `getEntitlements`, `restorePurchases`, `identifyUser`, `logout`, `observeEntitlementChanges`. **Interface names are candidates, NOT verified react-native-purchases SDK signatures.** No SDK/network, native plugins, API endpoints, migrations, subscription/payment mutators or client secrets. Disabled by default.
- `CandidateProduct` requires unique `productKey`, platform-specific mock opaque `store_app_ref/store_sku_ref`, same Starry app_id/brand/platform/environment; no live price, SKU, bundle or external revenue record exposed. `official_product_approved:false` always, registered candidate listings `sellable:false`. Cross-app app_id or provider scope mismatches are denied, even when users share central Starry Auth.
- `getEntitlements` reads only test-only separate Billing SQLite local candidate and hypothetical floor **twice**, with lawful purpose preflight + postflight. Revoked/refunded/expired always nonauthorizing; local active/grace/hold also unverified. Expiry / cancellation / renewal / refund / missing notification / restore require signed server events, monotonic versions, legal Auth binding, anti-PITR floor and reconciliation not provided by these mocks.
- Return `EntitlementView` v0 contains no member_ref, Store transaction, SKU, raw receipt, price or PII. Every result has `official_store_verified=false,identity_mapping_approved=false,purchased=false,subscription_active=false,lifetime_unlocked=false,ads_suppressed=false,can_restore=false,may_grant=false,may_regrant=false,may_ack_queue=false,may_publish=false,may_purchase=false,live=false`. *Removing ads* must be driven by **same-App valid non-consumable remove_ads/lifetime unlock or a live authorized subscription that explicitly includes ad removal**, only after real server verification; a client cache, app-level boolean, an unrelated App's purchase, mock RC webhook or direct Store callback is never sufficient.
- Forever FREE Starry Battery cannot be an IAP SKU, receipt reward, paid subscription perk or purchase route; sticker/topup unsafe keys rejected. Ads/rewarded ads **must not** be converted into Battery purchase reward without separate domain approval. H-Global and all its orders/credentials excluded.
- Node test loads **two physically separate disposable SQLite `:memory:` DBs**, local Billing event candidate vs hypothetical independent version floor. Tests cover per-App isolation, unsigned Store, refund/revoke/expire/grace/hold, replay/PITR/stale version, same SKU reuse, legal changes, malicious getters/Proxy, duplicate requests, no-ad protection, no active products and permanent free Battery. Their `offline` PASS does not demonstrate signed Apple/Google/RevenueCat purchase proof.
