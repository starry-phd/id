## 3. 唯一 W2 review vocabulary（**提案，不是已審核的 wire contract**）

為避免兩位 Owner 在整合時擅自 rename，同一詞只表示一件事，請 AI-0 考慮採用以下**概念命名表**，須逐欄做 schema/source gate：

- `source_issuer_identity`：a proven server-origin issuer identity; NOT a registry pointer
- `issuer_registry_ref`：opaque origin/provenance registry pointer; NOT issuer identity
- `verification_key_id`：key ID in issuer-scoped key registry; NOT issuer ref
- `integrity_proof`：typed kind/algorithm_id/encoding/value plus verified coverage; NOT an automatic rename of signature, integrity_signature or R005 mac
- `business_core_digest`：hashed identity of committed canonical business core; NOT proof signature/MAC
- `source_auth_version`：event origin Auth-version snapshot; not consumer-time read
- `observed_auth_version`：consumer-time server Auth read; not signed source snapshot
- `source_session_version`：event origin SessionVersion; not active-session requirement for revoked events
- `observed_session_version`：consumer-time SessionVersion monotonic fence; not always source equality
- `source_actor_pseudonym`：nonreversible event actor reference, not raw member ID
- `source_session_pseudonym`：nonreversible event session reference, not Session ID
- `server_actor_reference`：trusted internal actor resolved by server, not hash alias
- `server_member_reference`：trusted internal member resolved by server, not hash alias
- `business_core_schema_version`：Layer1 business version only
- `security_envelope_schema_version`：Layer2 security version only
- `proof_issued_at`：envelope proof creation clock; NOT business occurred_at
- `proof_nonce`：issuer-scoped replay nonce requiring durable fence

簽章類型建議使用**型別化概念** `integrity_proof {kind,algorithm_id,encoding,value}`，而非直接把 AI1 `signature` 別名為 AI3 `integrity_signature`；只有未來可信 key verification 的結果可證實。若 `kind=mac`，不可當成非對稱簽章。正式 wire-format/演算法/版本/欄位、儲存、kid rotation 均由 AI-0 與 AI-1／AI-4 安全審核，這裡不實作 signer、parser 或 shared schema。

**版本相容策略：** Layer1 `schema_version` 仍是 ADMIN-PREP 十一核心的業務 schema，特定需要時 `idempotency_key` 條件性欄位；Layer2 獨立 `security_envelope_schema_version` 概念。待批准後才可建立明確 `(business_core_schema_version,security_envelope_schema_version,issuer_key_epoch,proof_kind)` 版本配對 allowlist；不認識的版本或未提供可信來源一律拒絕。**無法推導 G06 未列明的第13欄，不把 R006 17 欄提升正式版。** `occurred_at`≠`proof_issued_at`；source SessionVersion ≠ observed current SessionVersion；簽章前後欄位版本不能偷換。

## 4. 關鍵修訂：server revoke/delete authority 與一般 notification 是兩種安全流程

| 分類 | 可信來源權威 | Auth／Session 重查語義 | Delivery／ACK |
|---|---|---|---|
| `SERVER_COMMITTED_REVOCATION_OR_DELETION`（`identity.session.revoked、identity.member.deleted`） | AI-1 Auth unique writer verified source transaction, committed revoke/delete record, durable original outbox and server-level issuer provenance (all require future approval) | `DO_NOT_REQUIRE_ACTIVE_MEMBER_SESSION_AFTER_REVOKE`：Verify Auth-version/session-version monotonic transition and current revoked/deleted state + exact source event; stale current state/restore floor unknown block effects but preserve audit/recovery route for evidence review | Server-origin transition may remain eligible for future reliable audit routing even though member is revoked/deleted. This is a DESIGN route, NOT live send/ACK now.；**`may_send=false, may_ack=false`** |
| `USER_NOTIFICATION_DELIVERY`（`notification.delivery.queued`） | approved signed source + scope; separate from Auth member revoke provenance | `REQUIRE_CURRENT_ACTIVE_AUTH_SESSION_WHEN_POLICY_APPLICABLE`：Current member active, not revoked/deleted, session not expired, consent/preferences, recipient minimization, ordered message and legal policy must all pass at delivery | No user notification after account deletion or revoked/expired session without separately approved lawful exception and signed server-only basis.；**`may_send=false, may_ack=false`** |

**會使撤權永遠無法送稽核的錯誤：** 對 `identity.session.revoked`／`identity.member.deleted` 的**server-authorized transition event**，用「已被撤權/刪除的會員 Session 現在必須 active」當必要前置條件。既然撤權正常完成後 Session 必然無效，這種設計將永久無法通知稽核域，並破壞 D87 committed outbox→target inbox 的可靠性。正確**待審方向**是：AI-1 唯一 Auth writer 已**原子提交撤權/刪帳狀態與原始 outbox**；AI-0/AI-1 通過 server-origin proof/issuer scope、原始事件、事件版本與**目前已撤權／已刪除狀態＋monotonic floor** 查證，在非會員活動 Session 下仍允許未來**受控稽核處理候選**（不是用過期 token 代替身份）。若 post-transition 發現更晚的刪帳狀態，可評估保留不可逆 audit fence，而不是重新要求 active。若來源不可信、floor 不明、Q104/Q119 未決、簽章不可信，**只可 blocked/review**。

一般 `notification.delivery.queued` **不同**：需要當下被允許的有效會員 Session／帳號、同意/偏好/權限、已驗來源及 recipient minimization；撤權、刪帳、過期後不可借「server revoke 允許稽核」這條規則續送一般通知。更不能將 server audit/revoke 的憑證共享給一般 user notification。

真實程式互證：AI-1 [R004 fence](https://github.com/starry-phd/id/blob/7316ee0f014a01649eea87a62b3ad6cdb6b1febd/modules/starry-id-v1/src/wave1-round004-event-session-fence.ts) 已區分 `notification.delivery.queued` 要求 `status=active`／未 revoked，而撤權／刪除事件要求 `state=revoked/deleted`；但它仍是**離線審閱**，不能據此解禁真 Queue／issuer，也沒有取代 AI-1 仍需明確標準化的 D87 source commit/outbox 證明。
