## Actual code vs unimplemented boundary
- `oidc-crypto.ts` verifies **real RS256 JWS** against server-pinned JWKS keys (no URL from JWT), exact Apple/Google issuer, intended Client ID aud/azp, nonce, iat/nbf/exp and provider stable subject. `verifyPkceS256` actually checks SHA-256 S256 challenge. `createVerifiedOidcCallback` verifies server OAuth attempt and one-winner CAS then delegates **real code exchange** to AI-4 trusted interface. No live Apple/Google JWKS download, code exchange, platform key trust management or account creation; this is a cryptographic implementation tested with ephemeral RSA keys, **not a live login**.
- `session-crypto.ts` issues/verifies **real WebCrypto HMAC SHA-256** (inject non-extractable server key from secret manager; CI uses ephemeral key). Scope, TTL ≤15 min, key version `kid`, anti-tamper; still must resolve **current** Starry D1 Member/Session/AuthVersion/Provider identity through `createServerIdentityResolver`; signed JWT alone not a login principal. Session revocation and status changes invalidate.
- `d1-ports.ts` uses fixed parameterized D1 `prepare().bind().first()/run()`, brand/app/runtime read isolation, integer privacy normalization, Active Member/Session provider lookup, StoreBinding lookup and profile/session CAS changedRows=1. Bind from trusted Worker `env`; never use HTTP to select table/database. SQLite schema + in-memory tests only; **no Cloudflare binding, no D1 deployment, no real transaction concurrency Gate**.
- `003_starry_oauth_round3.DRAFT.sql` one-use OAuth attempt state CAS; server-only PKCE verifier must be held securely outside untrusted DB/browser. Actual user provisioning, linkage and pending-revocation callbacks require separate approved transaction and auditable actor decisions.

## AI-4 exact server composition next step
1. Worker registry pins `brand_id='starry'`, app_id/environment/provider client ID. Redirect to Google/Apple using a random server-generated state/nonce, S256 code challenge and backend-held verifier.
2. On callback, worker backend reads stored OAuth attempt, checks state/PKCE, atomically consumes once, exchanges code at legitimate provider TLS endpoint, and verifies returned `id_token` via `createVerifiedOidcCallback` and trusted rotating Google/Apple JWKS. Never trust claims from `request.json()`.
3. Fetch immutable `(provider,sub)->s_user_id` binding from Starry ID DB; create/rotate Session atomically with secure HTTP-only SameSite cookie or short-lived bearer and CSRF measures. Existing 2nd round Auth Port stays per-request server-only.
4. For each protected request, validate `createVerifiedSignedSession(opaqueRequest, trustedNow)` using a server-only HMAC CryptoKey; its **now must be supplied by the Worker trusted clock**, since `createServerIdentityResolver` invokes the injected verifier with only the opaque request; then use AI-1 `createServerIdentityResolver({verify_oidc_or_session,read_member,read_session,identity_matches,trusted_scope})`; **never convert raw session claims to principal**. AI-4 alone controls Workers routing/SDK/OpenAPI and zero-trust request boundary.
5. Profile mutation: call `planSelfUpdate` after principal+fresh member, then `createStarryD1Port(db,scope).updateProfileCAS(...)` and check exactly one changed row. Revocation: `revokeSessionCAS` and commit before responding. Cross-domain deletion requires single-owner transactional outbox / audit from AI-3, not this PR.

## Gate blockers / safety
- Real provider JWKS secure fetch/cache/rotation, clock skew policy, exact OIDC provider configurations, secret key management, TLS code exchange and PKCE verifier storage/one-time state failure semantics; signed session cookie CSRF/rate limiting, refresh token rotation; account creation uniqueness and linking; D1 remote consistency/atomic multi-table delete; audit/Queue/notifications.
- D1 unit mock and SQLite memory do not prove Cloudflare D1 SQL execution, concurrency or Workers runtime. The new OAuth claim age/TTL is a candidate strict safety default requiring AI-0 policy; currently verification accepted only ≤10 minute-old token.
- Existing candidate directory fields, roles and break-glass, account binding lifecycle, two independent systems remain unaffected. No H-Global code, Payment, Production/real DB/secrets or actual deployed sign-in.
