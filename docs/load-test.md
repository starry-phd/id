# 壓力測試與容量評估（上線前）

規格「11.10、N08：2 萬人壓力驗收」簡化為「上線前以預估尖峰流量壓測登入與 Battery 預留；依實測數據決定擴充」。

## 1. 測什麼、怎麼測

| 項目 | 方式 | 何時執行 |
|---|---|---|
| 並發正確性 | `test/concurrency.test.mjs`：40 個同時預留搶 10 顆 Battery（必須剛好 10 個成功）、同一冪等鍵同時送 15 次（只建立一筆）、同一筆同時確認 10 次（只扣一次）、同一 Refresh Token 同時換發 10 次（最多一次成功）、同版本同時改資料 10 次（一次成功、九次 409）、同一新會員同時首次登入 25 次（只建立一位會員） | 每個 PR 的 CI |
| 負載 | `scripts/load-test.mjs`：每位虛擬會員依序 nonce → 登入 → 讀取會員 → 改資料 → 讀 App 設定 → 預留＋確認 Battery → 讀 Battery → 換發 Token；統計每個端點的 p50／p95，並檢查沒有任何失敗、Battery 總扣除等於會員數、沒有帳戶超過額度 | 每個 PR 的 CI（300 人、同時 50 人）；GitHub Actions →「Load test」可手動加大（預設 1,000 人、同時 100 人） |

限制：負載測試在 GitHub 的機器上以 workerd＋本機 D1 執行，量的是程式與 SQL 在並發下的行為與相對成本，不是 Cloudflare 全球網路的容量。staging 與 production 使用真實的 Apple／Google 驗證，無法用自動化帳號大量登入，這是刻意的安全設計。

## 2. 容量評估（2 萬名會員）

| 假設 | 數值 |
|---|---|
| 會員 | 20,000 |
| 每日活躍 | 20%（4,000 人） |
| 尖峰小時占全日 | 20%（800 人） |
| 每位活躍會員每次使用的 API 呼叫 | 約 30 次 |
| 尖峰小時平均 | 800 × 30 ÷ 3,600 ≈ 7 次／秒 |
| 瞬間尖峰（×10） | 約 70 次／秒 |

- **Workers**：依請求自動擴展，70 次／秒遠低於限制；Workers Paid 每月含 1,000 萬次請求，2 萬名會員約每月 300 萬次（含每分鐘排程）。
- **D1**：每個請求約 2～6 個查詢，尖峰約 140～420 個查詢／秒，都是有索引的單筆查詢或小批次。寫入集中在登入、換發、Battery；按領域拆成 identity、billing、battery 三個資料庫，Battery 的寫入不會跟登入搶同一個資料庫。
- **限流**（每個 Cloudflare 機房、每個 IP）：登入 30 次／分鐘、API 300 次／分鐘、網頁表單 20 次／分鐘；同一會員 API 300 次／分鐘。一般使用不會碰到；公司或校園共用 IP 大量同時登入時可能出現 429，App 依 `retry-after` 重試即可。
- **資料量**：D1 單庫上限 10 GB；每位會員的身分、資料、Session、稽核約數 KB，2 萬人遠低於上限。

**結論**：以目前架構，2 萬名會員不需要擴充。若 Workers Observability 中 D1 查詢時間明顯上升（p95 超過 50 ms），再評估 D1 讀取複本或拆庫（規格 F-07，需 ADR）。

## 3. 最近一次結果（2026-11-03，PR #33 的 CI）

300 位虛擬會員、同時 50 位，在單一 GitHub 機器的本機 workerd＋D1 執行：

- 2,700 個請求、8.6 秒（每秒 314 個），**失敗 0**；Battery 總扣除 300（等於會員數），**沒有帳戶超過額度**。
- 並發正確性測試 6 項全部通過。

| 端點 | 次數 | p50 ms | p95 ms |
|---|---|---|---|
| POST /v1/auth/nonce | 300 | 102 | 137 |
| POST /v1/auth/google | 300 | 237 | 296 |
| GET /v1/me | 300 | 111 | 159 |
| PATCH /v1/me/profile | 300 | 216 | 256 |
| GET /v1/apps/echo/config | 300 | 44 | 123 |
| POST /v1/battery/reservations | 300 | 245 | 285 |
| POST …/commit | 300 | 137 | 193 |
| GET /v1/me/battery | 300 | 134 | 186 |
| POST /v1/auth/refresh | 300 | 150 | 207 |

解讀：這些時間包含 50 個請求在同一台機器、同一個本機資料庫上排隊，用來比較端點之間的相對成本，不代表正式環境的回應時間（正式環境由 Cloudflare 各地機房分散處理）。最重的是登入、資料修改與 Battery 預留（都是寫入），也符合預期。上線後以 Workers Observability 觀察實際的 p95。
