## 2. Official provider behavior: high-risk facts to re-verify against actual Starry project

**Public official documentation checked as references on 2026-10-30; no account credentials or project configurations verified:**

- [RevenueCat Restore Behavior](https://www.revenuecat.com/docs/projects/restore-behavior): project-level setting impacts **all apps** in that RevenueCat project; the default **Transfer to new App User ID** can shift purchase ownership from an identified user to another during a restore, and settings can also apply on **new purchases** involving an already-associated receipt. "Keep with original App User ID" may block legitimate re-purchase on the same Store receipt; "Transfer if there are no active subscriptions" can still transfer non-subscription lifetime ownership. Anonymous App User IDs may alias instead of following identified-user transfer behavior. A separate Sandbox override is documented. These are **design hazards**, not evidence of how the unconfigured Starry project currently behaves.
- [RevenueCat Identifying Customers](https://www.revenuecat.com/docs/customers/identifying-customers): custom App User IDs are **project-scoped and case-sensitive**; one member identity across devices/platforms does not migrate the underlying Apple purchase into Google Play, nor permit App A to unlock App B. Map each app's Store application, RC project and SKU→entitlement through approved registry; no email or untrusted anonymous alias binding.
- [RevenueCat Restoring Purchases](https://www.revenuecat.com/docs/getting-started/restoring-purchases): `syncPurchases` may also trigger transfer/alias effects. Therefore **do not invoke restore/sync/new purchase to collect ownership proof** until the configured transfer behavior and proposed policy are independently reviewed and sandbox tested.
- [RevenueCat Webhooks](https://www.revenuecat.com/docs/integrations/webhooks): webhook authorization headers, optional HMAC signatures over raw body and timestamp, retries/duplicates, and delayed events require validated ingestion. A webhook alone is **not** official, fresh Store ownership or membership authorization. Persist accepted notification durably before HTTP acknowledgment; reconcile via trusted provider/Store API.
- [RevenueCat Testing Use Cases](https://www.revenuecat.com/docs/guides/testing-guide/use-cases): use sandbox isolated App User IDs, same Store account and transfer event checks to prove the configured policy. **Store app/project/SKU/RC account are only owner-reported, not verified**, so none of these tests is currently true G04/G05 evidence.

**Potential blocker:** RevenueCat default transfer is not compatible with a central Billing first-claim HOLD guarantee unless external RC restore/purchase behavior is separately configured and validated. Even if central Billing rejects a grant, client-side `restorePurchases` or new purchase **could have already changed RC attribution**. AI-0 must require live-account read-only inspection before policy selection or enabling the API/SDK call. This does not mean changing any provider setting now.
