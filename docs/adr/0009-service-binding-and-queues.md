# ADR 0009：Service Binding 與背景佇列（Cloudflare Queues）評估

日期：2026-11-07｜狀態：評估完成，**暫不實作**（沒有新增任何設定、資源或費用）。業主 2026-11-07 已同意這兩項可能產生的費用，因此達到下列重啟條件時可直接動工，不必再問。

## 現況

- App 後端用 `x-starry-app-key` 呼叫 `/v1`，限流走獨立的 `RL_APP` 桶（每金鑰每分鐘 3000），不吃 IP 限流。
- 刪帳清除（頭像、購買資料、Battery）寫入 `cleanup_jobs`，每分鐘排程重試，間隔遞增到 60 分鐘，最多 12 次，放棄後留在後台可見（`src/identity/cleanup-jobs.ts`）。
- 排程：每分鐘（釋放逾時預留、清除重試、用量暴增保護）與每日 03:17（維護、對帳）。

## Service Binding

- 費用：免費。
- 好處：App 後端不經公開網路、延遲較低。
- 為何不做：IP 限流問題已由 `RL_APP` 解決；每個 App 後端都要改 wrangler 並要求同一 Cloudflare 帳號；走內部直連會繞過網域層的 WAF 與路由，需另做一套驗證入口。
- 重啟條件：任一 App 的 `RL_APP` 常被觸發，或在意跨 Worker 延遲。

## Cloudflare Queues

- 費用：已核准的 Workers Paid 內含每月 100 萬次操作，超過每百萬次 US$0.40；一則訊息約 3 次操作（寫入、讀取、刪除）。依 Cloudflare 公開定價，動工前需再核對。
- 好處：內建重試與 dead-letter queue，大量扇出（公告信、推播）不卡排程。
- 為何不做：現有 `cleanup_jobs` 已有遞增重試與後台可見性；會員量為內部封測，沒有量；每分鐘排程仍需保留給 Battery 逾時釋放，Queues 不能取代；多一個元件就多一組 staging／production 資源與測試替身。
- 重啟條件（任一）：每日刪帳超過數百筆；公告信或推播一次要發給數千人以上；`cleanup_jobs` 常出現放棄項目。
- 若重啟，先只加「通知扇出」一條佇列，清除重試維持現狀。

## 結論

兩項都不做。需要業主同意的前提（可能產生費用）也因此不會發生。
